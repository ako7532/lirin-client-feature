## Bug 1 — Twin Souls blocked by the duel toggle even when the duel is idle

### Root cause

`resolve_minigame_owner` (lines 951–967):

```python
def resolve_minigame_owner(duel_enabled, duel_owns, twin_souls_enabled, twin_souls_owns):
    if duel_owns:          return "duel"
    if twin_souls_owns:    return "twin_souls"
    if duel_enabled:       return "duel"          # <-- the problem
    if twin_souls_enabled: return "twin_souls"
    return None
```

`_TwinSoulsArbiterOwner` (3011–3016) passes `duel_enabled = self.yinyang_duel_enabled`.
Because of the `if duel_enabled: return "duel"` line, **as long as the Yin Yang Duel
toggle is ON, the duel owns the slot forever**, regardless of whether the duel is
actually playing. `_DuelOwnsSlot` (3003–3009) correctly returns `False` when the duel
window `state` is `0` (idle), but `duel_enabled` short-circuits the arbitration back
to `"duel"` anyway.

Result: while the duel toggle is on, `PollTwinSouls` reaches line 3164–3170, sees
`owner == "duel"`, and prints **"waiting for Yin Yang Duel"** even when the duel is
idle, on cooldown, or at its daily limit.

The current test **enshrines** this behavior — `test_client_feature_local.py` line 1193:

```python
assert resolve_minigame_owner(True, False, True, False) == "duel"   # both enabled, neither owning
```

### Fix direction (design decision required)

The duel should own the slot only while it has work to do, and should yield to Twin
Souls when it is idle/finished/on cooldown/at limit. Options (choose and document):

- Keep `duel_enabled` out of the tie-break; make `duel_owns` reflect "duel can act
  right now" (actively playing `state in (2,3,4)`, or idle-but-startable: not on
  cooldown and below the daily limit). When the duel is idle-and-cannot-act, return
  `"twin_souls"`.
- Or add an explicit "duel is available to start" signal to `resolve_minigame_owner`
  so `duel_enabled` alone never claims the slot.

Whatever you choose, update the test at line 1193 and add cases for:
duel idle/cooldown + twin souls enabled → `"twin_souls"`; duel at daily limit +
twin souls enabled → `"twin_souls"`.

### Resolution (applied)

Chose option 2 — an explicit "duel is available to start" signal. `resolve_minigame_owner`
now takes `(duel_enabled, duel_owns, duel_startable, twin_souls_enabled, twin_souls_owns)`
and `duel_enabled` alone never claims the slot; an enabled duel claims it only when
`duel_owns` (actively playing) or `duel_enabled and duel_startable` (idle, off
cooldown, below daily limit). `_TwinSoulsArbiterOwner` computes `duel_startable` via a
new `_DuelStartable` helper using a single `_DuelWindow()` lookup. Tests updated at
`test_client_feature_local.py` (~1190) plus new `_DuelOwnsSlot`/`_DuelStartable`/
`_DuelCloseResult` cases.

## Bug 2 — duel result screen not dismissed after finish

### Root cause

The finish→dismiss path has two fragile, reverse-engineered dependencies:

1. **Finish is only detected on a state transition** `prev_state in (2,3,4) and
   state == 0` (line 2759). If the game's `YinYangDuelWindow.state` does not return
   to exactly `0` after a match (e.g. a dedicated result/end state value), the
   `"finish"` event and the close schedule at lines 2769–2773 never fire.
2. **Dismissal calls a name-mangled private method** and only under `state == 0`:

   `_DuelCloseResult` (2663–2673) does
   `continue_btn = getattr(window, "_YinYangDuelWindow__OnResultContinue", None)`
   and calls it. If that method name is wrong for the current game build, or is not
   callable, `_DuelCloseResult` returns `False` and the result screen stays. The
   call site (2793–2798) also requires `state == 0`, so if `state` is not `0` the
   close is never attempted.

The runtime `state` values (`0` idle, `2` pick, `3`/`4` active) are reverse-engineered
and not verified against the current game build (see code comments around 2715 and the
existing handovers). Treat them as hypotheses to confirm.

### Fix direction

- First **observe the real `state` after a duel finishes**. The duel diagnostic
  (`DiagnosticYinYangDuel` / `_DuelDebugLog`, around lines 2456–2486 and 2784–2787)
  dumps `state`, scores, cooldown, and cards. Capture that log after a real finish to
  learn the actual post-finish `state` value.
- Confirm the correct dismissal for the result screen. The current
  `_YinYangDuelWindow__OnResultContinue` may be the wrong member for this build; the
  correct action may be a UI button reachable through the verified input adapter
  (see `Twin Souls`/Reaction adapters for the pattern), not a private method call.
- Make finish detection robust to the real state values, and schedule the close on
  whatever state the game actually enters after a match.

### Resolution (applied)

- Finish detection now fires on leaving the active states (`prev_state in (2,3,4)` and
  `state not in (2,3,4)`) instead of requiring `state == 0`.
- The result-screen dismissal is attempted after `YINYANG_DUEL_RESULT_CLOSE_DELAY`
  **regardless of the post-match state** (moved out of the `state == 0` gate), so a
  dedicated result state cannot leave it stuck.
- `_DuelCloseResult` now precedes every dispatch with `emit_synthetic_click()` (matching
  the reaction/duel card click paths), tries `YINYANG_DUEL_RESULT_CONTINUE_MEMBERS`, then
  discovers any callable result/continue/confirm member via `duel_result_continue_member`,
  and finally falls back to `window.Close()`.
- Added `_DuelFinishDiagnostic` — a one-shot log of the post-finish `state` and the
  window's result/continue/confirm/close/finish/end members — so the real dismissal
  member can still be confirmed on the next live run.

**Still needs live confirmation** (cannot be observed from unit tests): the actual
post-finish `state` value and the exact result-screen continue member for the current
game build. Capture the `Yin Yang Duel: finish observed at state=…` /
`result members = …` lines after a real finish to verify or pin them down.

## Interaction (fix both together)

If Bug 2 leaves `YinYangDuelWindow.state` stuck in `2/3/4` (result screen presented as
a non-zero state), then `_DuelOwnsSlot` returns `True` and keeps `duel_owns` set. That
independently blocks Twin Souls even after Bug 1's `duel_enabled` tie-break is fixed.
So fixing Bug 1 alone may not unblock Twin Souls; verify the duel window actually
returns to an idle state, and confirm both fixes together.
