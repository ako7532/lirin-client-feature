### 1.1 Explicit recorder-comparison hypothesis and stock-route risk

**H-AUDIT:** a candidate explanation for the disconnect is that a server compares recorder observations (click records/coordinates, periodic cursor and button state, aggregates, and queue VID-list snapshots) with queue activity and rejects an inconsistent sequence. This is a primary hypothesis investigated by this plan's evidence track; its mechanism and priority over other causes are not established. Live captures contain `recorder_enabled=1` and sample interval transitions from 100 to 40 ms during failing runs. Those observations establish recorder activity, not a server comparison rule or a kick reason. Injection, queue/combat behavior, account/session history and ordinary connection failures remain competing explanations.

**Stock-route profile:** the inspected stock add reaches `0x3ED760`, updates queue state and invokes `0x495EF0`; that helper marks the recorder's queue-list state dirty only when the recorder is enabled. It does not itself emit down/up records through `0x497840` or synthesize a cursor approach. An enabled recorder still independently takes code-0 cursor/button snapshots through `0x499340`, and its dirty queue snapshot is processed later. Manual input can also produce records independently. Therefore the precise prediction is **an API queue mutation with no accompanying click record generated by that API call**, not zero cursor samples, zero recorder records, or an immediate guaranteed VID-list upload for every mutation.

This differs from a manual actor click and from the old wrapper's synthetic down/up route. Whether the server accepts this profile while recording is enabled is an explicit unknown. The stock route is chosen for an auditable local queue contract; packet shape alone does not establish equivalence to manual play or solve H-AUDIT. Do not compensate for the profile by fabricating input, changing recorder settings, suppressing normal dirtying, or altering packets.

Every live stage must include the audit coverage and interpretation record in section 13.1. A run observed only with recording disabled or unknown cannot validate behavior while recording is enabled. The ladder probes the stock profile, but changes to injection, admission and transport also limit causal attribution; it is not a pure experiment isolating the server's audit algorithm.

### 3.2 New native observer interface

Expose a separate private module `_lirin_hunter_native` with API version 1. It provides **queries only**; all queue mutations stay in stock Python bindings. Registration must leave both the stock method definition and actual imported `player.MetinQueueAdd` callable unmodified. Export `now_ms()` using Windows `GetTickCount64` as the common monotonic clock; no guessed game-clock units.

`snapshot()` returns a Python dict:

```text
api_version: 1
valid: bool
error: stable ASCII reason or None
player_cookie: current singleton identity token (internal, never dereference in Python)
vids: immutable tuple of uint32 VIDs, in native queue order
enabled: bool
max_size: positive integer from verified stock query
observed_tick_ms: monotonic observation time
stock_binding_ok: bool (definition slot and imported callable verified)
```

`admission(vid)` returns `{valid, eligible, reason, player_cookie}`. It resolves a live actor within the call, rejects zero/out-of-range VID and non-stone targets, evaluates full native queue eligibility, and returns no raw actor pointer. `valid=False` means unreadable/unsupported; `eligible=False` means a valid rejection. Neither reads nor writes any picker, recorder, input, camera, attack, or queue state.

Validate before copying: singleton nonnull; all-null empty vector accepted; otherwise nonnull aligned begin/end/capacity; unsigned addresses ordered `begin <= end <= capacity`; byte spans divisible by 4; overflow-safe arithmetic; absolute sanity bound 1024 elements for both length/capacity. This bound is a corruption guard, not native queue capacity. Catch access faults and return invalid, never 'empty' or 'VID absent'. Copy only bounded data, then recheck singleton and vector metadata; invalidate on change. Execute on the verified game/Python update thread with GIL, not a worker thread.

The native add's capacity calculation excludes some entries; `len(vids)` is not necessarily effective native occupancy. Initial controller uses conservative `len(vids) < min(5,max_size)` and may underfill unusual queues rather than guess. Document this limitation; do not invent capacity arithmetic.

Register callables using verified CPython APIs, static-lifetime method definitions, proper new/borrowed references and exception rules. On partial registration failure remove the partial capability and keep Hunter unavailable. Audit query bodies for writes; module registration itself naturally changes Python module state. Do not promise an entirely write-free loader.

### 5.1 `HunterQueueGateway`

Dependencies: native observer, stock `player` module, current session getter. Methods: `snapshot()`, `admission(vid)`, `add_once(request)`, `remove_once(request)`, `set_enabled_once(value, lease)`.

Every mutation executes synchronously on the update thread; deadlines bound subsequent observation, **not** the duration of a native call. No background threads, blocking sleeps, or claim that Python timeouts can interrupt a hung native call.

A request records `{id, kind, vid, epoch, lease_id, player_cookie, created_ms, deadline_ms, dispatched, raw_return, last_snapshot}`. Set `dispatched=True` immediately before the stock call. Revalidate epoch, ownership, connected gameplay, cookie, admission and membership immediately before mutation. Issue each request at most once. Remove/enable/disable are separate tracked mutations, not hidden parts of add.

| Outcome | Definition | Next action |
| --- | --- | --- |
| `ALREADY_PRESENT` | Valid pre-snapshot contains requested VID; no add | Observe only; do not claim it was added/owned by Hunter. |
| `ADDED` | Valid pre-snapshot absent, valid immediate post-snapshot present, same epoch/cookie/lease | Record ownership under the exclusive session and permit later scheduling. |
| `REJECTED_PRECALL` | Required validation failed before setting dispatched | No mutation; candidate may be reconsidered only under policy below. |
| `REJECTED_NATIVE` | Verified stock add returns exact `0`, valid same-session post-snapshot remains absent | No fallback; back off this candidate for 2 s. This classification depends on the evidence gate for the unmodified stock API. |
| `REMOVED` | Valid pre-snapshot present, post-snapshot absent after one verified remove | Remove ledger entry. |
| `ALREADY_ABSENT` | Valid pre-snapshot absent; no remove | Remove stale ledger entry without mutation. |
| `UNKNOWN` | Exception after dispatch flag, invalid/missing post-snapshot, unfamiliar return, or unconfirmed requested membership | Retain request identity, freeze new additions, reconcile read-only. |
| `CANCELLED_PRECALL` | Epoch/owner/user intent changed before dispatch | No mutation. |

Stock truthy return alone never means ADDED. Wrapper codes `2/3/4` do not apply. An exception during the call must never become a certain rejection. Membership observed later means 'membership observed', not proof of causality if another writer intervened. Record that distinction. If add returns `0` but post-membership is present, stop with an invariant error rather than classifying it as a safe rejection; if an unfamiliar return accompanies presence, record presence but keep the request uncertain until the contract discrepancy is reviewed.

For `set_enabled_once`, verify enabled state and membership immediately after the call. A failed enable/disable with uncertain state enters the same reconciliation/error mechanism; it is not silently retried. For remove, the verified current contract plus pre/post absence determines the outcome, never only a truthy return. Every mutation type retains its own request record.

### 5.3 `HunterController`

Public methods: `start()`, `stop(reason)`, `pause(reason)`, `resume(token)`, `on_scan(snapshot)`, `tick(now_ms)`, `on_session_change(reason)`.

States: `OFF`, `STARTING`, `RUNNING`, `WAITING`, `RECONCILING`, `PAUSED`, `STOPPING`, `ERROR`. Store separate `user_requested_on`, pause reason, session epoch, lease, pending request, ownership ledger, rejection backoffs, priority state and next-add timestamp. Do not resurrect the old ever-queued set.

| Trigger | State/behavior |
| --- | --- |
| ON from OFF | STARTING; validate capabilities and exclusive lease; enable once; RUNNING only after valid enabled snapshot. Failure leaves OFF/ERROR with reason. |
| Normal tick with no candidate/full queue | WAITING; continue observations/scans, no mutation. |
| Candidate + capacity + schedule | RUNNING; issue one add; await exact outcome. |
| Any uncertain dispatched request | RECONCILING; no new additions or priority transitions. |
| Reconciliation succeeds within deadline | Resolve requested membership in same epoch; then RUNNING if intent/lease still valid. |
| Deadline expires | ERROR; retain audit record and quarantine VID for this epoch; quiesce owned native automation using section 6 cleanup; no automatic retry. |
| Reaction safety | PAUSED after native queue is actually quiesced; resume only with valid token/checks. |
| OFF/Stop | STOPPING; cancel pre-call work and clean owned native state; OFF after verified cleanup. |
| Session/phase/socket loss | Invalidate epoch, requests, resume tokens and lease; stop local scheduling immediately; do not call stale native singletons. |

UNKNOWN observation polls: next available update at or after 50 ms, for at most 2000 ms from dispatch. Missed frames never trigger catch-up mutation bursts. A valid absent snapshot after an exception does not establish that the original mutation never happened; allow observation until deadline, then ERROR. Preserve request history outside any diagnostic tracker that ages out.

ERROR prevents additions and triggers bounded cleanup when native state/ownership are valid. It must not leave a known Hunter attack queue running merely because the Python controller stopped. Cleanup does not retroactively turn an unknown addition into a rejection; preserve the original uncertain result and subsequent cleanup outcome separately.

An explicit OFF/ON restart can leave ERROR only after valid current snapshot, resolved native cleanup, and fresh lease acquisition. It must not reuse a quarantined VID in the same epoch. No timer clears uncertainty automatically.

## 6. Session epochs, ownership, and Stop

### 6.1 Epoch

Use a monotonically increasing integer, not `gameplay_phase` itself. Increment on every registered gameplay window replacement/phase transition, socket loss, main-player replacement/map-session invalidation, feature shutdown/reload. Tokens capture epoch and player cookie. A `5 -> 4 -> 5` cycle and a new window in phase 5 both invalidate previous tokens. On gameplay re-entry remain OFF; never auto-enable from old state.

Use native `now_ms()` backed by `GetTickCount64`. If unavailable, Hunter is unavailable. Do not use wall-clock `time.time` for deadlines. Supply a fake monotonic clock in tests.

### 6.2 Exclusive lease

The first implementation does **not** attach to a manual queue. Start only when authoritative queue is empty and disabled, scanner is running, gameplay is connected, no Reaction safety pause exists, and no other automated queue writer is available. If queue is populated or enabled, keep OFF with `Queue: busy - stop manual queue first`. Do not clear it or silently adopt it.

Acquire a fresh lease id/epoch/cookie; enable the empty queue with one tracked operation. Record that Hunter owns this enabled session. Ownership ledger contains only absent-before/present-after successful additions in that lease, plus an explicitly tracked possibly-added VID while reconciling. Reconcile against current membership each tick; naturally consumed/despawned entries leave the ledger. Never clear a VID's quarantine simply because it is absent.

Unknown foreign VID, inconsistent enable state, or unexpected writer revokes exclusive ownership: freeze additions; retain current membership/provenance; report conflict. Do not bulk clear/disable a mixed queue. Snapshots cannot detect every concurrent manual remove/re-add of the same VID. Baseline contract therefore requires users to stop Hunter before manually editing its queue; do not claim perfect concurrent manual ownership protection. Do not install input hooks to guess provenance.

### 6.3 Stop and cleanup

1. Set `user_requested_on=False` for explicit Stop/OFF; pause keeps intent separately. Prevent subsequent additions before any cleanup call.
2. Cancel only undispatched work. Dispatched uncertainty is retained for observation/cleanup, never labelled 'never executed'.
3. In valid gameplay with exclusive lease and every remaining VID proven Hunter-owned (or its pending request under unchanged exclusive provenance), disable once through stock API; this performs the full native clear. Observe disabled+empty. Do not also call clear redundantly.
4. If foreign members exist, keep enabled state unchanged; use verified `MetinQueueRemove(vid)` for only known Hunter-owned VIDs, once each, bounded by the ledger (max five ordinary entries plus any reconciled priority transition). Verify absence after each call. Unknown/conflicting VIDs remain for manual resolution. Do not remove an already-absent VID or blindly repeat a failed remove.
5. If cleanup is uncertain, remain ERROR with explicit residual-queue status. Button OFF means no future additions; status must distinguish 'native cleanup incomplete' from 'stopped'. No 'Queue cleared' claim without observation.
6. If phase/socket/singleton is invalid, cancel local work and avoid native mutations. Report cleanup unconfirmed; do not resurrect old queue state on next login.

General feature Stop must call this lifecycle and stop scanner scheduling. Remove broad Hunter calls to `ClearNativeAutomation`/`ClearTarget`/attack-key mutation that could affect a manual queue after a failed lease. Existing unrelated global emergency semantics must not be reached accidentally through an unavailable feature.

## 7. Exact continuous-refill policy

Defaults are controller policy, not inferred server requirements:

- Target capacity `min(5, stock max_size)`; invalid/nonpositive max makes Hunter unavailable.
- One add at most per `tick`, one outstanding mutation, and at least **1000 ms between add attempts**. First candidate can be added on the first valid RUNNING tick after enabling.
- Refill whenever a valid snapshot has a vacancy and a candidate exists, including when queue reaches zero. There is no 'wait until batch empty' rule and no 35–70 s refill timer.
- `REJECTED_PRECALL` for one stale candidate permits selecting a different candidate on a later tick. `REJECTED_NATIVE` backs off that VID for 2000 ms. Do not iterate through many mutations in one tick.
- Unknown outcome freezes all new adds. No next-scan retry of that VID or another VID while unresolved.
- Full queue waits for the next authoritative vacancy; no camera/projection requirements, random jitter, probability-based refill or occasional anti-detection pauses.

### 7.1 Update-loop integration order

Keep one controller instance per panel/script lifetime. `ToggleMetinHunter` delegates ON/OFF intent to it; it must not perform an independent enable/clear operation. Replace each old reset/phase/Reaction call site explicitly; do not retain two sources of Hunter state.

On each existing watcher/update callback, execute this order:

```text
1. Read monotonic time and update existing gameplay/socket/phase observations.
2. Process session invalidation first; reject all stale tokens/requests.
3. Poll Reaction safety, regardless of automatic solver availability.
4. Process Stop/pause/error cleanup and pending request reconciliation.
5. If scanner is due and gameplay allows discovery, publish a fresh scan snapshot.
6. If Hunter is OFF, PAUSED, STOPPING, ERROR, or still reconciling, render status and return.
7. Read/reuse the current valid queue observation; verify binding identity, cookie and lease.
8. Reconcile ledger and detect foreign membership/enable-state changes.
9. If priority policy is enabled, advance one priority transition/request and return if busy.
10. If full, no candidate, stale scan, or before next_add_ms, set WAITING and return.
11. Select one candidate; perform final live/native checks and issue one add request.
12. Set next_add_ms = actual attempt start + 1000; process immediate result; render status.
```

Existing early returns for Reaction, hidden UI or scanning must not bypass step 4. Paused mode forbids additions, but pending cleanup/reconciliation still runs. Recheck session/cookie after any callback capable of changing gameplay before executing a mutation. A `tick` never calls itself recursively.

### 13.1 H-AUDIT probe and evidence criteria for every stage

Treat recorder-enabled state as an observed exposure/configuration, not a verified server comparison window. Do not force recorder enablement, intervals, flushes or input records to obtain exposure. For the uninjected control, recorder state may be unavailable: record `UNKNOWN` unless existing independent logs actually establish it. Do not inject for observation and continue labelling that control 'uninjected'.

Maintain one row per stage/session/configuration interval with:

```text
stage, PID/build, observation method and maximum gap
recorder state: observed-enabled / observed-disabled / unknown
effective sample_ms and flush_ms; start/end bounds and missing coverage
app-active/focus conditions; manual input observation/source or unknown
queue request ids/counts and membership outcomes under each observed configuration
flush/dirty-list evidence: observed state only / send-path observed / payload decoded / unknown
disconnect source/time; monotonic interval from relevant observations when comparable
trial result and which claims the coverage supports
```

If estimating exposure duration from polling, label it estimated and retain gap/transition uncertainty; do not present interval sums as exact active-audit seconds. For each stage write one of `AUDIT-EXPOSED`, `NO ENABLED STATE OBSERVED`, `UNKNOWN COVERAGE`, or `NOT RUN`, with supporting counts. 'No enabled state observed' does not exclude a short interval missed by polling.

- **Manual controls (stages 1–2):** establish comparable connection/queue behavior, audit settings when observable, and whether actual manual click records/payload are observed or only expected. A manual run without enabled exposure is not a matched control for an enabled automatic run.
- **Discovery-only (stage 3):** establishes whether a recorder-active session can remain stable with the new injection/observer and no automatic queue mutations. It does not test stock-add acceptance.
- **One stock add (stage 4):** explicitly probes the absence of an API-generated click while recording is observed enabled, if that exposure occurs. Verify actual queue membership; distinguish normal independent periodic samples from per-click records. Without decoded/send evidence, describe the predicted profile rather than claiming specific bytes reached the server.
- **Continuous/priority (stages 5–6):** assess repeated queue transitions and cleanup while recording is observed enabled; record settings/counts per interval and delayed disconnect observations. Do not change refill policy within a run to 'improve' audit appearance.

Interpretation must be hypothesis-aware without arbitrary weights: a disconnect following enabled recorder activity and automatic queue mutation is consistent with H-AUDIT but is not proof. Comparable exposure in stable manual/discovery controls and repeatable differences make the hypothesis more informative. Enabled activity in stable automatic runs provides evidence for those observed conditions; it cannot eliminate cumulative/session rules. A disconnect when no enabled state was observed challenges an immediate-audit-only explanation only to the extent observation coverage is complete; gaps, previously buffered records, delayed sends and cumulative scoring remain alternatives.

Do not promote temporal coincidence to a kick reason or assign a numerical confidence/weight without a justified analysis. If no enabled exposure occurs, finish/report the bounded trial and mark **H-AUDIT acceptance untested**; do not extend play indefinitely, fabricate an audit, or call the stock route validated under audit. Repeat comparable trials only when the user requests them.
